# Журнал зарядки EV — что сделано, как и почему

## Зачем это вообще понадобилось

История зарядок в приложении зарядника ("X Smart EVSE") — единственный источник данных о кВтч, стоимости и длительности сессий. Полагаться на то, что приложение никогда не сбросит и не забудет эту историю, нельзя. Нужен был независимый журнал — свой, не привязанный к производителю зарядной станции.

Дополнительное требование, которое стало ключевым: заполнять журнал нужно с нескольких устройств (свой телефон, комп, лаптоп, телефон жены), при этом все должны видеть один и тот же актуальный журнал, без ручного экспорта/импорта между устройствами. Установка приложений на телефоны исключалась — только открытие ссылки в браузере.

## Что сделано (итоговая версия)

Собран самостоятельный HTML-файл `index.html` — один файл, без внешних зависимостей, работает как мини-приложение в любом браузере. Выложен на GitHub Pages, данные хранятся в общем облачном сторе JSONBin.

**Функциональность:**
- Ввод новой сессии: дата, энергия (кВтч), цена за кВтч (по умолчанию подставляется последняя введённая — не нужно каждый раз набирать 0.65), время начала и окончания, пробег/одометр (км), произвольная заметка (например "14А" или "после солнца").
- Автоматический расчёт: стоимость сессии (кВтч × цена), длительность из разницы времени начала/окончания (с обработкой перехода через полночь), средняя мощность сессии (кВтч ÷ часы).
- Сводка наверху: суммарные кВтч (с анимированным "прокручиванием" счётчика при добавлении записи), число сессий, итоговая стоимость, средние кВтч на сессию, средняя мощность по всем сессиям с указанной длительностью.
- **График по месяцам:** кВтч (столбики) и стоимость ₪ (линия с точками) по каждому месяцу. Собственный SVG на чистом JS, без внешних библиотек и интернета для отрисовки — не зависит от CDN.
- Редактирование записи: кнопка ✎ подставляет значения обратно в форму, "Добавить запись" превращается в "Сохранить изменения", появляется "Отмена".
- Удаление записи — через подтверждение ("Удалить? Да / Нет"), чтобы случайный клик по "×" не стирал строку сразу.
- Экспорт CSV — выгрузка всех записей в файл (с BOM для корректного открытия в Excel).
- Импорт CSV — обратная загрузка файла с сопоставлением по названию колонки (а не по номеру), поэтому старые CSV без новых колонок по-прежнему импортируются нормально. Уже существующие записи (совпадающие по дате + кВтч + длительности + заметке) пропускаются, чтобы повторный импорт не дублировал строки.
- Индикатор синхронизации в шапке (точка + текст): "синхронизировано", "сохранение…", "нет связи — локально", "нет ключа".
- Локальный кэш: данные показываются мгновенно из памяти браузера, затем обновляются из облака; при отсутствии связи журнал продолжает работать оффлайн.

**Оформление** сознательно отсылает к реальному электрощитку (по фото): пронумерованные "слоты" записей — как позиции автоматов в щите, зелёная точка-индикатор — как LED на автоматах ETEK, медно-янтарный акцент — в цвет медной шины на фото щитка Hager.

## Как это устроено технически (итог)

- **Хостинг файла** — GitHub Pages. Репозиторий `charging-log` (Public), файл называется `index.html` (Pages показывает по корню ссылки именно его). Постоянная публичная ссылка вида `https://<логин>.github.io/charging-log/` — не меняется при правках кода, не зависит от аккаунтов Claude и их планов.
- **Хранение данных** — общий облачный стор JSONBin. Bin ID зашит прямо в файл (константа `BUILT_IN_BIN_ID`), поэтому на каждом устройстве вводится только Master Key. Все устройства читают/пишут в один и тот же бин — отсюда общая синхронизация.
- **Master Key** хранится в `localStorage` каждого браузера отдельно (вводится один раз на устройство). В файл он НЕ зашит — это ключ ко всему аккаунту JSONBin, поэтому его нельзя выкладывать в код или переписки. Bin ID зашивать безопасно, Master Key — нет.
- Приватность: сам HTML публичен по ссылке, но без Master Key данные из бина не прочитать. Для домашнего журнала зарядок это разумный уровень.

## Почему ушли от прежней схемы (window.storage в артефакте Claude)

Первая версия (v1) хранила данные через `window.storage` — API персистентного хранилища артефактов Claude. От неё отказались по цепочке причин, всплывших на практике:

1. `window.storage` работает только у **опубликованной** версии артефакта — черновик/превью в чате данные не сохраняет.
2. Каждая новая публикация после правки кода создаёт **новую ссылку с пустым хранилищем** — обновить существующую "на месте" нельзя. Из-за этого изначально и добавили экспорт/импорт CSV как страховку перед каждой правкой.
3. `window.storage` и опубликованный артефакт намертво привязаны к аккаунту, из которого артефакт опубликован. Работа начиналась на free-плане личного аккаунта Claude; free-план быстро исчерпался, пришлось перейти на рабочий аккаунт RAD — и старая ссылка стала выдавать "Artifact not found" (данные остались в личном аккаунте).
4. Не хотелось ради личного журнала постоянно сидеть в рабочем аккаунте.
5. И главное требование — синхронизация между несколькими устройствами и людьми (телефон жены) — через `window.storage` в принципе не решалось чисто: оно работает только внутри одного аккаунта Claude.

Автономный HTML с `localStorage` тоже отпал: не зависит от Claude, но данные лежат в каждом браузере отдельно — синхронизации между устройствами нет вообще. Вывод: единственная схема, дающая общий журнал на всех устройствах без привязки к аккаунту Claude — общий бэкенд. Выбрали "GitHub Pages (постоянная ссылка) + JSONBin (общее хранилище)".

## Развилки, которые проходили

- **Хостинг:** сначала пробовали Netlify Drop (анонимно, без аккаунта). Он выдал ссылку, но поставил на сайт свой пароль ("Password protected site"), убрать который без входа в аккаунт Netlify нельзя. Аккаунта Netlify не было, а на GitHub личный аккаунт уже был — перешли на GitHub Pages, публичный по умолчанию.
- **Хранилище данных:** сравнивали JSONBin и Supabase. Supabase — полноценная БД, мощнее, но настройка сложнее (таблицы, ключи). Для журнала зарядок избыточно. Выбрали JSONBin как простейший key-value стор: регистрация, один бин со значением `{ "defaultPrice": 0.65, "entries": [] }`, Master Key.

## Правка от 26.07.2026: поле пробега/километража

По образцу экрана Ioniq 5, где под каждой зарядкой показан километраж:

- В форму добавлено поле **«Пробег, км (одометр)»** после времени окончания (общий счётчик машины, не суточный трип).
- Пробег показывается в строке записи (напр. "12 480 км"), сохраняется при редактировании.
- CSV расширен колонкой «Пробег км»; импорт читает её по имени, старые CSV без неё импортируются нормально (просто без пробега).

## Правка: формат времени

Поля времени начала/окончания сессии первоначально были нативными `<input type="time">` — а такой инпут показывает 12- или 24-часовой формат в зависимости от локали браузера/ОС, а не от самого HTML. Универсального атрибута "покажи 24 часа" не существует.

Заменили на пару простых числовых полей **ЧЧ / ММ** для начала и для окончания — всегда 24-часовой ввод, без сюрпризов на любом устройстве. Внутри данные по-прежнему хранятся строкой "ЧЧ:ММ" — остальная логика (расчёт длительности, CSV) не менялась.

## Решили НЕ делать: автоматическое подтягивание тарифа IEC

Возник вопрос — можно ли автоматически вытягивать актуальный тариф с сайта IEC вместо ручного ввода. Проверили и отказались от идеи:

- Страница IEC рисует тариф через JavaScript в браузере — сырой HTML-запрос (что прямой, что из кода журнала) не содержит числа вообще.
- Даже если бы это не мешало — сработал бы **CORS**: браузер блокирует такие кросс-доменные запросы к чужому сайту независимо от того, вызван запрос автоматически или по кнопке.
- Чтобы реально прочитать цифру, нужен headless-браузер (Selenium/Playwright) — то есть отдельный сервис, который надо где-то регулярно гонять и чинить при любом изменении вёрстки сайта.
- К тому же "тариф" — не одно число: единый тариф, тариф теу"ז (по часам/сезонам), плюс возможные скидки у частного поставщика.

Тариф меняется пару раз в год по решению регулятора — не тот случай, где нужна инфраструктура. Решили оставить как есть: поле цены запоминает последнее введённое значение, при изменении тарифа достаточно один раз вписать новое число. Классический случай **YAGNI** (You Aren't Gonna Need It) — не строить то, что не понадобится.

## Как теперь вносить изменения (освоенный цикл)

Ссылка постоянная, данные в облаке — правка кода больше НЕ стирает историю и НЕ меняет ссылку. Порядок:

1. Просим Claude внести изменения в код → получаем новый `index.html`.
2. В репозитории `charging-log` на GitHub: **Add file → Upload files** → перетаскиваем новый `index.html` (заменяет старый) → **Commit changes**.
3. Через ~1 минуту GitHub Pages пересобирает сайт. Ссылка та же, данные в JSONBin не тронуты.
4. Обновляем страницу на устройствах (на телефоне иногда нужно закрыть вкладку и открыть закладку заново). Master Key вводить заново не нужно — он сохранён в каждом браузере.

## Настройка нового устройства

1. Открыть постоянную ссылку в браузере, добавить в закладки.
2. В жёлтом баннере вверху вставить Master Key из JSONBin (раздел API Keys). Bin ID уже зашит — вводится только ключ.
3. Нажать "Подключить" — устройство подтянет общий журнал, ключ сохранится.

Для жены и остальных: ничего устанавливать и регистрировать не нужно — открыл ссылку, один раз вставил тот же Master Key, готово.

## Текущий статус

- Журнал живёт в git (GitHub Pages), синхронизация между устройствами через JSONBin подтверждена рабочей в оба конца.
- Цикл "правка кода → Upload на GitHub → обновление сайта без потери данных" пройден вживую.
- Экспорт/импорт CSV работают и остаются штатным способом бэкапа.
- Пробег per session пока не ведётся регулярно (неудобно снимать на ходу) — но поле уже готово, график расхода на 100 км появится, как только накопятся пары показаний одометра.
- Следующие возможные графики (обсуждались, не сделаны): расход кВтч/100км, средняя мощность сессий по времени, привычки по дням/часам зарядки.
